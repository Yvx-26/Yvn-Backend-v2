# 可靠接收与故障恢复

## 当前部署状态

代码与隔离测试已实现。按用户要求，**仅生成迁移文件，不对当前数据库执行，不自动重启服务**。
启用前先人工执行 `migrations/ingestion_receipts.sql`，再更新并重启后端。
当前数据库的既有采集表、定位表和历史记录不需要改结构或清空。

如果先启动新版而未执行迁移，MQTT 收到的消息仍会持久化在本地，后台因回执检查未就绪暂停，
页面不会获得这些消息的新帧。积压达到上限后会停止确认新消息，等待消费恢复。
因此不要把“服务能启动”当成“链路已完成部署”。

## 处理流程

```text
EMQX QoS 1 / 持久会话
  -> MQTT 网络回调
  -> 本地 SQLite 接收队列事务提交（WAL + synchronous=FULL）
  -> 手动 PUBACK
  -> 波形、定位各一个后台消费线程
  -> /emqx/ingestion-health（消费前检查回执能力）
  -> 原有 HTTP 接口 + Idempotency-Key
  -> MySQL 原始帧与回执原子提交
  -> 解析样本与完成回执原子提交
```

HTTP 接口只异步读取 JSON，其余同步数据库与解析工作交给线程池，避免占用事件循环。
两条消费通道分开，单条波形慢请求不占用 MQTT 网络回调或定位消费线程。
数据库连接、读取、写入和 HTTP 都设置有限超时。

## 消息标识和保证范围

- 本地每条事件使用稳定接收标识。HTTP 超时、重启恢复与后台重试都沿用同一标识。
- 原始帧编号与回执在同一 MySQL 事务；提交已经成功但确认丢失时，重试复用该编号。
- 样本写入暂时失败，原始帧保留，只重试样本；入库时的线路/长度快照也随回执保留。
- `Idempotency-Key` 不能被用于另一份内容，冲突返回 409。
- 本地记录 MQTT 会话内 Packet ID，只有 `DUP=true` 且内容/通道一致才复用旧事件。Packet ID 重用的新发布不会被误删。
- **相同波形内容不等于重复消息**。不同真实上报即使内容相同也会分别保存。
- 推荐让 EMQX 重发布 JSON 增加 `event_id`，值取原始规则事件的唯一 `id`，并保留真实 `clientid`。
  例如波形规则可选择 `id AS event_id`，重发布 JSON 增加 `"event_id":"${event_id}"`。
  定位同理使用每条原始发布的独立标识，不要把设备编号或相间编号当事件标识。
- 没有源事件标识的旧 EMQX 规则仍可用：可以识别会话内 QoS 重发和本地重试，但不能可靠判断
  “上游重新发布的一条独立消息”是否其实是业务重复。不会按内容或时间戳猜测后丢弃数据。
- 旧 HTTP 调用不带幂等键仍兼容，但无法获得跨请求去重保证；直接 HTTP 的发送方应提供稳定幂等键。
- 不是无条件的端到端 exactly-once：Broker 会话到期、源端未投递成功、损坏/丢失本地磁盘、
  删除回执、无标识的独立重复发布，都不在当前机制可完全消除的范围内。

## 启用顺序

1. 保留数据库备份和原部署文件；在隔离环境执行迁移并验证，再由操作者决定生产执行时机。
2. 人工执行新增回执表 SQL。原始帧、定位、样本与回执必须使用 InnoDB 事务表。
3. 为后端保留持久可写目录 `var/`；容器部署需挂载持久卷，不使用临时目录或多个主机共享网络文件。
4. 确认 `.env.example` 中新参数，按实际部署填入 `.env`。相对队列路径以后端根目录为基准。
5. 更新、重启后端。先确认 `GET /emqx/ingestion-health` 返回 `idempotency: true`，再检查新帧持续入库。
6. 在隔离环境验证 DB 短暂不可用、HTTP 确认丢失、MQTT 断线和服务重启。当前没有进行真实 Broker 故障演练。

新版使用 MQTT 3.1.1 `clean_session=False`、订阅 QoS 1、`manual_ack=True`。
Broker 必须允许持久会话与离线缓存；缓存容量、有效期要按最长故障时间配置。
波形/定位重发布不应使用 retained 旧消息冒充新实时事件；需要 retained 时务必提供稳定源事件 ID。
同一 Broker 的 Client ID 不能被另一机器复用。

本地对 Broker/Client ID 和队列路径分别持有进程锁，防止同机重复实例顶连接或抢队列。
Bridge 应保持单实例；Web 层多 worker / 多机部署需要将 Bridge 独立部署，不能简单复制当前配置启动。

## 本地队列与恢复

默认文件：`var/mqtt-inbox.sqlite3`，以及配套 WAL/SHM 和锁文件。
不能为了清缓存删除 `var/`；其中可能包含已向 Broker 确认、但尚未入库的唯一副本。
运行中的备份应使用 SQLite 备份能力或先安全停止 Bridge，不能只复制主文件而漏掉 WAL。

| 状态 | 含义 |
| --- | --- |
| pending | 已落盘，等待处理或到期重试 |
| processing | 正在处理；重启时恢复为 pending |
| done | MySQL 完成；本地清空原消息正文，保留去重记录 |
| dead | 非法消息、永久拒绝或超过重试次数；正文和错误仍保留 |

默认指数退避 1、2、4、8…秒，最大间隔 60 秒；最多 10 次后进入 dead。
回执迁移未就绪或消费前健康检查失败不会消耗消息尝试次数。
已经确认的无效帧只归档一次，不会无限尝试把坏帧解析成正常波形。
迟到的定位消息不会覆盖时间戳更大的位置；相等的非零时间戳也不刷新在线时间。
无时间戳的旧 GPS 保留兼容，但无法可靠排序其多个独立上报。

查看状态（只读，不打印消息内容）：

```powershell
python -m app.services.ingestion_queue --path var/mqtt-inbox.sqlite3
```

查明并修复失败原因后，**先停止 Bridge**，再显式重新排队 dead 消息：

```powershell
python -m app.services.ingestion_queue --path var/mqtt-inbox.sqlite3 --retry-dead
```

重新排队沿用原事件标识，不生成新业务事件。未经修复的坏消息仍会被隔离。
不要通过删除本地队列或清空 MySQL 回执来“解除故障”。
已完成的本地记录默认保留 7 天后清理；pending、processing、dead 不自动删除。
MySQL 回执不自动清理，后续归档策略必须覆盖源端重发与人工恢复的最长周期。

## 资源上限

- 默认未完成容量 10000 条，含 dead；满时断开并暂停接收，不把新消息静默丢掉。
- 默认单条 MQTT 消息最多 256 KiB；超限不确认，需要检查源消息或调整上限后恢复。
- 磁盘写入失败时不确认；后台检查写入/容量恢复后重启 MQTT 网络循环，让持久会话重发。
- dead 长期积压需要人工审查、备份和处理，不能认为它们已成功入库。
- `var/` 已加入 Git 忽略规则；自定义路径也必须避免把原始消息上传到仓库。
